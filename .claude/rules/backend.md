# Backend: FastAPI relay (Python 3.11 in Docker)

- Runs on `python:3.11-slim` (pinned by digest in `backend/Dockerfile`); the host has 3.12, so avoid 3.12-only syntax (for example same-quote nesting inside f-strings). Dependencies are pinned in `backend/requirements.txt`; dev/test-only deps (`pytest==9.1.1`, `httpx==0.28.1`) are in `backend/requirements-dev.txt`, layered on top (`-r requirements.txt` first).
- No business routes: `GET /health` (internal — the container `HEALTHCHECK` and the proxy network use it) and `GET /api/health` (the same handler, also registered at that path, routed publicly by nginx and read by the uptime monitor) are the only endpoints, both returning `{"status", "service", "environment", "revision"}` — `environment`/`revision` come from `Settings` and prove what's actually deployed. Swagger and ReDoc are disabled.
- Settings: `src/core/config.py` (pydantic-settings `BaseSettings` with `extra = "ignore"`, so unknown env keys are tolerated and every field has a code default: the app boots even if an env file never reached it). Real config comes from the compose `env_file` chain (`env/<env>.env` then optional `env/<env>.secrets.env`), not from `backend/.env` (legacy, being removed). Never read `backend/.env` or any `env/*.secrets.env`; use `env/secrets.env.example` (or the legacy `backend/.env.example`) for variable names.
- Logging: `src/utils/logging.py` (Rich console + JSONL request log under `logs/`); no `print()`.
- Tests: `backend/tests/` (pytest, `TestClient` fixture in `conftest.py`) covers `/health`+`/api/health` response fields, CORS preflight (allowed vs. foreign origin) and `Settings` parsing (JSON-list `CORS_ORIGINS`, unknown-key tolerance, defaults, `ENVIRONMENT`/`REVISION` passthrough) — always build a fresh `Settings(_env_file=None)` in a settings test, never reuse the module-level singleton. `.github/workflows/ci.yml`'s `backend` job runs `python -m pytest -q` with `requirements-dev.txt` installed, on Python 3.11, on every push to `master` and every PR. A host venv is impossible here (python3.12-venv missing, no sudo): run pytest in a throwaway `python:3.11-slim` container with `requirements-dev.txt` installed (see `/deploy-check`).
- The `runtime` image stage runs as non-root uid 10001 (user `app`, no shell/home) and installs only from the `builder` stage's prebuilt wheels (`--no-index --find-links=/wheels`, no compiler, no network); `wheel`, `setuptools` and the `jaraco.*`/`pkg_resources` packages setuptools vendors are uninstalled/removed afterward since they're fixable-CVE sources never needed at runtime (`pip` itself stays). `ARG GIT_SHA` (passed by CI) becomes `ENV REVISION`, which is what `/health` reports.
- Images are built in GitHub Actions, not on this box: `images.yml` builds the `runtime` target once per green `master` commit, scans it with Trivy (blocks on fixable HIGH/CRITICAL), and points `:dev` at it (and `:stage` while `STAGE_AUTO_PROMOTE=true`). A manual `docker compose build backend` here is break-glass only (see root `CLAUDE.md` golden rule 2).
- To see a change live before a release: push to `master`, then check `dev.yuriodev.co.uk/api/health` once the deploy agent (cron, within a minute) has recreated `yuriodev-dev-backend`. Its config is `env/dev.env` (+ optional `env/dev.secrets.env`) — never read the secrets file, and never `deploy/dev/backend.env` (same legacy status as `backend/.env`).
