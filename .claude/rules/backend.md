# Backend: FastAPI API (Python 3.15 in Docker)

- Runs on `python:3.15-slim` (pinned by digest in `backend/Dockerfile`); the host Python is older and is never used for the backend, so 3.15 syntax is fine (PEP 695 generics, unparenthesised `except A, B:` which ruff format enforces for a py315 target). Dependencies are pinned in `backend/requirements.txt` (including `httpx`, the outbound HTTP client, also used by the tests' `TestClient` and `httpx.MockTransport`); the dashboards data API adds SQLAlchemy 2.1 (async, with `greenlet`), `asyncpg`, `alembic` and the official `mcp` 2.x SDK (plus three pinned transitive packages of `mcp`: `httpx2`, `httpcore2`, `python-multipart`; every pin is a release at least two weeks old with a CPython 3.15 wheel, because the image has no compiler: check both before bumping); dev/test-only deps (pytest, pytest-cov, ruff, mypy) are in `backend/requirements-dev.txt`, layered on top (`-r requirements.txt` first). Tool config (ruff, mypy strict, pytest, coverage) lives in `backend/pyproject.toml`.
- Layout: `src/main.py` is only `app = create_app()` (uvicorn target `src.main:app`); `src/app.py` is the factory (logging, middleware, error handlers, routers); `src/routes/` holds one router per feature; `src/core/` holds config, schemas, errors, logging, middleware, plus the shared feature plumbing (`clock.py`, `http.py` the one outbound client, `snapshot.py`, `refresh.py`); `src/feed/` is the social feed package; `src/dashboards/` is the dashboards data API (below), its REST router is `src/routes/dashboards.py`; `src/deps.py` the `Depends` seams (handlers read `request.app.state.settings`, never a module global).
- Routes: `GET|HEAD /health` (internal — the container `HEALTHCHECK` and the proxy network use it) and `GET|HEAD /api/health` (routed publicly by nginx, read by the uptime monitor) both return `{"status", "service": "yuriodev-api", "environment", "revision", "ref"}` — `environment`/`revision`/`ref` (the branch the image was built from, `build_ref`) come from `Settings` and prove what's actually deployed. Every error the app answers itself (404/405/422/500) is `{"error", "message", "request_id"}`, never input or a traceback. `GET|HEAD /api/posts` is the social feed (next bullet). Known gap: a 405 on the health paths says `Allow: GET` although HEAD is served (separate routes; Starlette names the first match). OpenAPI/Swagger exist only with `API_DOCS_ENABLED=true`, under `/api/openapi.json` and `/api/docs` (meant for dev; the Swagger UI assets are pinned to an exact `swagger-ui-dist` version in `src/app.py`); ReDoc is always off.
- Social feed, `GET|HEAD /api/posts` (ships **off**): `{version: 1, enabled, generated_at, source: {provider: typefully|fixture|none, status: fresh|stale|error|disabled, last_success_at}, items[]}`, one item per Typefully draft with per-platform `variants` (`x`: thread parts, `linkedin`: text) and permalinks; `Cache-Control: public, max-age=300`, a weak `ETag` over items + status, `304` on `If-None-Match`. Always 200/304: off gives `enabled: false, items: []`, upstream trouble only changes `source.status`, and the route only reads memory (visitors can never trigger a Typefully call). Code: `src/feed/` — `normalize.py` is the only place raw drafts become models (strict allow-list; `extra="forbid"` models in `schemas.py`; styled Unicode kept verbatim, no NFKC; control/bidi characters stripped; paid partnerships, the X side of subscriber-only posts, LinkedIn reshares and X Articles dropped), `providers/typefully.py` (one listing page of up to 50 published drafts, `get_draft?exclude_comment_markers=true` only for new or changed drafts, rate-limit headers honoured; the key is a `SecretStr`, sent per request, never logged; bodies are requested uncompressed and capped at 2 MiB, any gzip/deflate inflated in bounded steps in `core/http.py`), `providers/fixture.py` + `fixtures/drafts.json` (synthetic drafts for local/dev/stage, private fields hold `*-SENTINEL` strings), `curation.py` + `content/posts.toml` (pin/feature/hide by id and hand-added `[[native]]` posts; parsed strictly, shipped with commented examples only), `service.py` (incremental cycle, 30 min ±10% with exponential backoff, `fresh` within 2× the interval, `error` after `SOCIAL_FEED_MAX_STALE_HOURS`=72 without a success, when imported posts are withheld and curated ones kept; >50% invalid drafts keep the previous snapshot: `schema`, `incomplete` (an enabled platform or a permalink without its posts/text/time, e.g. a renamed field), `bad_url` and `fetch_failed` count, deliberate drops do not; a listing with any unusable row is rejected whole; a draft whose fetch returns an unusable answer is skipped until it changes, not the cycle). The poller is a background task started in the lifespan only for `typefully`; startup and `/health` never wait on it. Settings (all off/empty by default): `SOCIAL_FEED_ENABLED`, `SOCIAL_FEED_PROVIDER` (`fixture`|`typefully`), `TYPEFULLY_SOCIAL_SET_ID`, `TYPEFULLY_API_KEY` (secret: `env/prod.secrets.env` only), `SOCIAL_FEED_REFRESH_SECONDS` (1800), `SOCIAL_FEED_MAX_ITEMS` (12), `SOCIAL_FEED_MAX_STALE_HOURS` (72), `SOCIAL_FEED_EXCLUDE_TAG` (`hide-from-site`), `SOCIAL_FEED_SNAPSHOT_PATH` (unset = memory only; the image has a writable `/app/data`). Turning it on is an env change plus a backend recreate, described in `deploy/README.md` ("Social feed"). `tests/test_feed_leak.py` proves no private draft field (scratchpad, title, tags, private/share URLs, media ids) reaches the body or the snapshot file: keep it green.
- Dashboards data API (ships **off**; contract: tasks and calendar events for the spaces `personal`, `work-1`, `work-2`, over REST and MCP). Switch: `DATABASE_URL` (secret, `env/<env>.secrets.env`): unset means `GET /api/dashboards/v1/bootstrap` answers `{"enabled": false, "spaces": [], "areas": [], "server_time"}` without authentication and everything else under `/api/dashboards/**` and `/api/mcp` answers 503 `dashboards_disabled`; nothing else in the backend changes (stage and prod stay in this state for now; dev has a database). Code in `src/dashboards/`: `models.py` (SQLAlchemy tables `space`, `area`, `task`, `event`), `migrations/` + `db.py` (Alembic), `runtime.py` (engine, session factory, `ready` flag), `service.py` (all queries and rules), `schemas.py`, `gate.py`, `mcp_server.py`, `catalog.py` + `areas.json` (spaces, area seed; the Russian names live in JSON so Python stays ASCII). Rules worth knowing:
  - **Gate** (`gate.py`, pure-ASGI middleware added innermost so CORS preflights pass and 401/503 still get a request id and access line): for every request under `/api/dashboards` and `/api/mcp` it adds `Cache-Control: no-store`, answers 503 when disabled (bootstrap excepted), then 401 `unauthorized` unless `DASHBOARDS_TRUST_PROXY_AUTH=true` (dev/stage only: nginx basic auth already ran; never in prod) or the `X-Dashboards-Token` header equals `DASHBOARDS_API_TOKEN` (SHA-256 both sides, `hmac.compare_digest`). Not `Authorization`: basic auth owns it on dev. Neither configured means closed. Names of constants avoid `token`/`password` (ruff S105).
  - **Startup never waits on the database**: the lifespan creates the engine (`DashboardsRuntime`), starts the MCP session manager and a background task that runs `alembic upgrade head` in a worker thread, retrying 1 s, 2 s ... 30 s until the database answers; until then every call is 503 `dashboards_unavailable` (so is bootstrap: a half-started database must not look like "sample data"). A URL the driver rejects is logged once by class and leaves the API unavailable. Migrations: `src/dashboards/migrations/` (env.py is async/asyncpg, online only, takes `pg_advisory_xact_lock` inside the migration transaction so processes started together migrate once; forward-only; revision ids `dashboards_NNNN`, the first seeds the spaces and the ten personal areas); `backend/alembic.ini` only serves a dev shell (`DATABASE_URL` set). Constraint names follow `models.NAMING_CONVENTION`; keep migrations and models in step by hand (no drift test).
  - **REST** `/api/dashboards/v1`: `GET /bootstrap`, `GET /summary` (`{"spaces": {"personal": {open, priority, overdue, next_event}, "work-1": ..., "work-2": ...}}`, all three always present; `next_event` is `{title, starts_at}` of the space's earliest event that has not ended yet, or null; overdue = open with `due_date` before today), `GET|POST /spaces/{space}/tasks` (`{"tasks": [...]}`, `?status=open|done|all`, open first: priority, due date nulls last, oldest; done after, latest first), `PATCH|DELETE /tasks/{id}`, `GET /events?from=&to=` (`{"events": [...]}`, events of all spaces intersecting the days (both included, in `DASHBOARDS_TIMEZONE`), at most 62 days, `from <= to`), `POST /spaces/{space}/events`, `PATCH|DELETE /events/{id}`. Bodies reject unknown fields; PATCH changes only the fields sent (`notes`, `area_id`, `due_date` accept null to clear); setting `status` maintains `done_at` (kept when already done, cleared on reopen); an area must belong to the task's space (personal only); event times need a UTC offset and are stored and returned in UTC (`...Z`). Unknown space or id (including a non-UUID) is 404, bad input 422, both in the app's `{error, message, request_id}` shape via `core.errors.AppError` (fixed sentences: never request input). A task belongs to one space and every task query filters on it: the only multi-space reads are the calendar and `summary`/`today` (grouped per space). "Today" (summary overdue, MCP `today`, day ranges) is the date in `DASHBOARDS_TIMEZONE` (IANA name, default `Europe/London`, validated at startup, `tzdata` pinned so the slim image needs no system zone data) taken from the app's clock (`create_app(clock=...)`). Task fields: `id, space_id, title, notes, area_id, priority, due_date, status, done_at, source, created_at, updated_at`; event fields: `id, space_id, title, starts_at, ends_at, busy_only, source` (the frontend relies on these exact sets).
  - **MCP** `POST /api/mcp` (streamable HTTP, stateless, JSON answers; GET is 405 so nothing holds a stream open; the SDK's Host check is off, the gate is the defence): tools `list_tasks`, `add_task` (`area`, source `mcp`), `update_task` (empty string clears notes/area/due_date), `complete_task`, `reopen_task`, `delete_task`, `today`, `list_events(from_date, to_date)` (`from` is a Python keyword and the SDK passes arguments by Python name), `add_event`, `delete_event`; compact JSON text results; errors are `ToolError` with fixed sentences. The route is only added when the API is on; the lifespan runs `server.session_manager.run()` (once per app: `create_app` builds a new server each time). Works behind uvicorn's `--ws none --no-access-log` (plain HTTP request/response).
  - **No client text in logs.** SQLAlchemy would log statements with parameters at DEBUG (dev runs `LOG_LEVEL=DEBUG`) and a driver exception message quotes them, so `core/logging.py` pins `sqlalchemy` and `mcp` to WARNING and `service.guarded` turns every `SQLAlchemyError`/`OSError` into 503 `dashboards_unavailable` logging only `operation` and the exception class (`from None`, no chained traceback). MCP tools log unexpected failures by class only. `tests/test_dashboards_logs.py` greps every record (and the JSON stdout) for sentinel titles, notes and the token: keep it green. Never put input into an exception message or a log field.
  - SQLAlchemy 2.1 deprecations are errors under `filterwarnings = error`: `select().distinct(col)` is gone (use `.ext(postgresql.distinct_on(col))`, as `service.summary` does).
- Collectors (`src/dashboards/collectors/`; off unless `DATABASE_URL` and a credential are set): `GITHUB_TOKEN` (open PRs you authored and PRs with a review requested from you, REST search with `author:@me` / `review-requested:@me`, `GITHUB_SEARCH_SCOPE` appended, titles `PR #n: t` / `Review PR #n: t`, external id `owner/repo#n:author|review|reviewed`; `review` also covers review requests to the owner's teams (`GET /user/teams`, then `team-review-requested:<org>/<team>` for at most ten teams of the scope's `org:`; a token that may not read teams gets none, any other failure of that call fails the fetch), `reviewed` is the one query `reviewed-by:@me -author:@me -review-requested:@me`) and `LINEAR_API_KEY` (GraphQL `viewer.assignedIssues`, state type not completed/canceled/duplicate, title `ID: t`, external id the issue id, due date used only at creation); target spaces `GITHUB_SPACE` / `LINEAR_SPACE` (`personal` or `work-1`, default `work-1`, `work-2` refused by `CollectorSpace` in `core/config.py`); `DASHBOARDS_COLLECT_INTERVAL_SECONDS` (30..86400, default 300). `manager.py` is the loop (started in `_start_dashboards` once the schema is ready; first tick at once, then every interval; each collector isolated; a session-level `pg_try_advisory_lock` on a dedicated connection so one process polls; rate-limited sources paused per `base.pause_seconds`; logs only collector name, counts, `kind`/`status`/error class), `sync.py` the upsert. A collector's `fetch` returns the COMPLETE open set or raises (`UpstreamError("incomplete")` for 1000+ search hits, a flagged incomplete answer or more than 10 pages): absence means closed, so a partial answer must never be returned. Rows are normal `task` rows with `source` `github`/`linear` and a collector-owned `stage` (migration `dashboards_0004`: Linear state type `started|unstarted|backlog|triage`, else null; GitHub `mine`/`review`/`reviewed` by role; in `TaskOut` and the MCP output, rejected by `TaskPatch`/`TaskCreate`, not part of the tombstone fingerprint) (the check constraint was extended, no parallel field), `source_ref` = external id (partial unique index on `(source, source_ref)`), `url` (new; in `TaskOut` and the MCP output). Collector-owned ordering and marking fields (migration `dashboards_0010`, in `TaskOut` and the MCP output, rejected by create and patch, null/false for manual tasks): `source_priority` (`urgent|high|medium|low|none`, Linear's `priority` 1,2,3,4,0; unknown numbers give null; NEVER the user's boolean `priority`, which is the hand-picked Priority panel), `source_updated_at` (Linear `updatedAt`, GitHub search `updated_at`), `draft` (GitHub search `draft`); all come in the same answer, no extra call. `service.task_order` sorts open tasks: the manual `priority` flag, then the source priority (urgent first, a manual task after them all), then `source_updated_at` newest first (nulls last), then due date and age as before. Ownership: the collector rewrites title, url and status (a task finished by hand reopens while the item is open); priority, notes, area, due date and space are never touched. Items that left the set are marked done, never deleted. Deleting a collected task writes a `task_tombstone` row (fingerprint = sha256 of title + url, written by `service.delete_task`, REST and MCP alike); the sync skips an item whose tombstone fingerprint still matches, recreates it when title or url changed, and drops tombstones of items no longer open. Outbound calls use `core/http.py` (`get_json_capped`, `post_json_capped`: no redirects, capped body, errors reduced to a kind); tests fake the transport with `httpx.MockTransport` (`tests/collectors_support.py`) and set `app.state.collector_transport` for the wired-in app. Never log a title, url or token; names in tests and docs are invented (`example-org/sample-repo`, `ENG-1`).
- Calendar collector (`collectors/ical.py`, `sync.sync_events`; migration `dashboards_0003`): `CALENDAR_ICS_PERSONAL` / `CALENDAR_ICS_WORK_1` (secret comma-separated https iCal URLs; no work-2 setting) and optional `CALENDAR_OWNER_EMAILS`; one `CalendarCollector` per space (name `calendar-<space>`). Libraries `icalendar` and `recurring-ical-events` (pure Python; the latter has no `py.typed`, hence the mypy override in `pyproject.toml`; the parse runs in `asyncio.to_thread`). Per feed: `core.http.request_capped` (5 MiB cap, `text/calendar`-ish media types, conditional GET, in-memory copy for 304), expansion for today-7d..today+60d in `DASHBOARDS_TIMEZONE`, `event` rows with `source='calendar'` and `source_ref` = `<space>|<UID>` (series instances `<space>|<UID>|<original start UTC>`); the collector owns all fields of its rows, deletes rows that intersect the window and left the feeds, and deletes nothing when any feed of the space failed; hand-made and MCP events (other `source`) are never read. Declined = `PARTSTAT=DECLINED` for an address in `CALENDAR_OWNER_EMAILS`; cancelled = `STATUS:CANCELLED`; PRIVATE/CONFIDENTIAL = `busy_only`. A feed URL is a credential: held as `SecretStr`, feeds are named by index in logs, errors are `UpstreamError` kinds, the parser's own exception text is never kept (`bad_ics`). `Collector` is now `collect(client, sessions, now) -> counts`; task collectors share `sync.TaskCollector` (fetch + `sync_items`). Tests: hand-written feeds in `tests/calendar_support.py`, never a real calendar.
- Projects (user-created dashboards beside the three spaces; `src/dashboards/projects.py`, `src/routes/projects.py`, migration `dashboards_0005`): the registry is `project` in the main schema (`id` slug `^[a-z0-9][a-z0-9-]{0,30}$` made from the name by `slugify`; `icon`, nullable, a key `^[a-z0-9-]{1,24}$` into the frontend's drawings (migration `dashboards_0006`): the backend stores and shape-checks it only, `POST` takes it optionally, `PATCH` sets it and `null` clears it, and it is in every project shape incl. `GET /bootstrap`'s `projects` and the MCP `add_project(name, icon)` / `list_projects` (Cyrillic transliterated via `translit.json`, never one of `personal`/`work-1`/`work-2`/`calendar`), `name` 1..40, `archived`, `schema_version`, `created_at`); each project's tasks live in schema `project_<id with - as _>`, table `task` (the space task's columns minus space, area, url, stage and collector fields; `source` web/mcp; no events, no areas). The three spaces are untouched. **Schema name**: built only in `schema_name()` from an id that passed `valid_id`, then handed to SQLAlchemy as `Table(schema=...)` / `CreateSchema(...)` (it quotes); an invalid id in a URL is a 404 before any query, so request text never reaches SQL (`test_a_hostile_project_id_never_reaches_sql`). **Creating** a project inserts the registry row and runs `PROJECT_STEPS` up to `SCHEMA_VERSION` in one transaction (a failure leaves neither). **Migrating the schemas later**: Alembic migrates the main schema only; each project's `schema_version` is brought up to the code's by `upgrade_projects` (called by the runtime after the Alembic upgrade, so it is retried with it): to change the per-project table, bump `SCHEMA_VERSION` and add `PROJECT_STEPS[n]` (the n-1 to n step, plain SQL through `connection.execute`); it runs once per project in its own transaction under an advisory lock that re-reads the version, so processes starting together cannot double-apply. **Nothing ever drops a schema**: there is no delete, only `archived` (reads still work; writes are 409 `project_archived`; PATCH can unarchive). REST: `GET|POST /projects`, `PATCH /projects/{id}` (`{name?, archived?}`), `GET|POST /projects/{id}/tasks`, `PATCH|DELETE /projects/{id}/tasks/{task_id}`, with the space endpoints' bodies, ordering (`service.task_order`, shared) and `done_at` rule; a task is `TaskOut` with `project_id` for `space_id` and `area_id`/`url`/`stage` always null; an `area_id` in a body is 422; `GET /projects` returns `{projects: [{id, name, archived, open, priority, overdue}]}`, archived ones flagged; `GET /bootstrap` adds `projects: [{id, name}]` (not archived); a taken id (or a reserved one) is 409 `project_exists`, a name with no letter or digit 422. MCP: `list_projects`, `add_project(name)`; `list_tasks`, `add_task` and `today` take a project id in their `space` argument (space ids are reserved, so it is unambiguous); the id-based tools (`update_task`, `complete_task`, `reopen_task`, `delete_task`) take an optional `project` because a task id alone does not say which table it is in. The test fixture drops project schemas between tests (the app never does).
- Finance (`src/dashboards/finance/`, migration `dashboards_0007`; ships **dark**: needs `DATABASE_URL` and `MONOBANK_TOKEN`, a `SecretStr` in the secrets file; no token means no collector, no HTTP client for it and no outbound call): read-only bank data in its own Postgres schema `finance` (`models.py` has its own `FinanceBase` with `schema="finance"`, so it is never in `models.Base`; the migration is hand-written like the others). Tables: `connection` (provider, ref, `status` ok|needs_reconsent|paused, last_ok_at, last_error: the one shared place for "is this link healthy"; provider-specific auth or consent state must go in tables of the provider's own, never here), `account` (provider, external_id, name, type, currency, `mask_last4` (a CHECK of four digits: never a full card or IBAN), `balance`/`credit_limit` bigint minor units, balance_at, archived, and the collector's cursors `synced_until`, `backfilled_from`, `backfill_done`, `empty_streak`), `transaction` (account, external_id unique per account, booked_at, `amount` bigint minor units + `currency`, `original_amount`/`original_currency` only as a pair, description, counterparty, `category_code` (Monobank: the MCC), `balance_after`, `pending`, `internal_transfer` (migration `dashboards_0008`: set by a provider when the counterparty is another account of the same owner; Monobank sends a counterparty IBAN for business accounts only, compared in memory with the owner's own IBANs, never stored; nothing reads the flag yet)). **Money is an integer in minor units next to an ISO 4217 alpha code, never a float**: the parsers reject floats and bools (`monobank.whole`), the columns are `BigInteger`, sums come back as `Decimal` and are converted with `int()`. Collector: `base.py` has the neutral `AccountData`/`TransactionData`, the `FinanceProvider` protocol (`fetch_accounts`, `fetch_statement` for one page, plus `min_call_gap`, `refresh_every`, `max_window`, `page_limit`) and `FinanceCollector` (the `Collector` protocol, so it runs under `CollectorManager`, a second instance with its own interval `FINANCE_POLL_INTERVAL_SECONDS` and its own advisory lock `FINANCE_LOCK_KEY`, built in `_start_dashboards`, `app.state.finance_collectors`, sharing the one HTTP client). One tick makes at most one provider request and never two within `min_call_gap` (in-memory `_next_call_at` against the manager's clock; a rate-limit answer also pauses the collector through `pause_seconds`). Order of work: accounts and balances every `refresh_every` (20 min), then per account the newest window (`synced_until` minus a 3-day overlap, so a hold that settles is updated by the upsert on `(account_id, external_id)`), and only when nothing is due one backward window (`backfilled_from`) until `FINANCE_BACKFILL_MONTHS` (default 12, 0..36) or, for an account with no known opening date, three empty windows in a row (an account with `opened_at` is walked back to it however long the quiet stretch, bounded by the depth and the provider's history floor). A window is fetched whole in memory (further pages when a page is full, up to 10) and written in one transaction with the cursor move: a failed or partial fetch changes nothing and the window is asked again from scratch. An `auth` failure sets the connection `needs_reconsent` (retried every 20 min; a good call sets it back); `paused` (by hand in SQL) makes no call. Monobank (`monobank.py`, limits checked against https://api.monobank.ua/docs/ v250818: `X-Token`, client-info and statement each once per 60 s, a window at most 31 days + 1 hour, amounts in minor units, `time` Unix seconds, newest first; the 500-item page is observed, not documented): 61 s gap, 31-day windows; the item's `currencyCode` is documented as the account's currency, so an original amount is stored only when it differs from the account's; jars are accounts of type `jar` (their statement is asked for the same way), managed clients and the webhook are not used; an unlisted numeric currency is stored as `XXX`. **Privacy is stricter than for tasks**: never log an amount, description, counterparty, account number or the token (logs carry the collector name, counts, `status`/`kind`; the manager logs a tick with `calls: 0` at DEBUG only); `tests/test_dashboards_logs.py` has the finance sentinels: keep it green. Read API `routes/finance.py` under `/api/dashboards/v1/finance`, same gate, no write endpoint: `GET /accounts` (`{accounts, connections}`, open accounts first; `balance` is as the provider sends it, `own_balance_minor` = balance minus credit limit), `GET /transactions` (`account`, `from`/`to` days in `DASHBOARDS_TIMEZONE`, `q` (case-insensitive, `%`/`_`/`\` escaped), `min_amount`/`max_amount` signed minor units, `limit` 1..200 default 50, opaque `cursor` over `(booked_at, id)`; `{transactions, next_cursor}`, newest first), `GET /summary` (`{month, as_of, currencies: [{currency, accounts, balance, own_balance, spent, received}]}`: balances of open accounts, this month's money out and in). MCP: `finance_accounts`, `finance_balances`, `finance_transactions(query, account, from_date, to_date, min_amount, max_amount, limit, cursor)` (`finance/mcp.py`, fixed-sentence errors). Tests: `tests/finance_support.py` (`FakeMonobank` follows the documented rules, `seed`), `test_finance_{monobank,collector,api,mcp,app}.py`; names and amounts are invented.
- Money page data (migration `dashboards_0011`, `finance/categories.py`, `finance/maintenance.py`): accounts carry `kind` (`current|credit_card|savings|pot|business`; Monobank: a card with a credit limit is `credit_card`, `fop` is `business`, a jar is `savings`; Monzo: from the account type, pots are `pot`), `label` (a neutral sub-type: Monobank's tier, Monzo's "Personal"/"Joint"/the type's own words; never the holder's name; two accounts of one type are told apart by `label`, `mask_last4` (Monzo: the last four of `account_number`) and `opened_at`), `parent_id` (a pot's current account, linked at store time), `goal_amount` (a pot's goal when Monzo's answer has one), `overdraft_limit` (a current account's, from the balance or account answer when present: `overdraft_limit` or `overdraft.limit`; never required) and the derived `available_minor` = balance + overdraft (a credit card's balance already counts its limit); `overdraft_limit_override` (migration `dashboards_0013`) is the owner's own figure, set by `PATCH /finance/accounts/{id}` or MCP `finance_set_overdraft`, written by no collector, and it wins over the bank's (`overdraft_limit_bank` still shows that one; `overdraft_limit_source` is `owner|bank|null`). Transactions carry `category` (the owner's override, else the normalised one, never null) and `category_overridden`, next to the raw `category_code`. The set is fixed (`categories.CATEGORIES`: housing_utilities, groceries, eating_out, transport, subscriptions, health, shopping, entertainment, debt, income, transfers, cash, other); `categorize(provider, code, amount, internal)`: an internal transfer is `transfers`, Monzo's own category or the ISO 18245 code (`MCC_RANGES`, first match wins) decides, unknown money in is `income`, unknown money out `other`. Collectors write `transaction.category` on every upsert; `category_override` is written by no collector, so a re-import keeps it; rows with a null category (older ones) are filled at startup by `fill_categories` (the `after_migrate` hook). A per-counterparty rule table is not built: it would fill `category_override`-like data at ingest, the columns are ready for it.
