# Frontend: React 19 + Vite 7 + TypeScript 5.9 (npm)

- Scripts (run in `frontend/`): `npm run dev` (vite on :5173; over SSH use VS Code port forwarding), `npm run build` (`tsc -b && vite build` -> `dist/`, gitignored), `npm run lint` (eslint 9 flat config), `npm run test` (`vitest run`; jsdom environment, `src/setupTests.ts`, see `App.test.tsx`), typecheck only: `npx tsc --noEmit -p tsconfig.app.json` (clean).
- `npm run lint` must stay at 0 problems: it blocks CI (and therefore image builds and every deploy). `npm run test` and `npm run build` block CI too.
- The build runs inside Docker (`npm ci` on node:26-alpine), so `package-lock.json` must stay in sync with `package.json`. Dependency changes (`npm install ...`) need Yurii's OK.
- Builds happen in GitHub Actions, not on this box: `.github/workflows/ci.yml`'s `frontend` job runs typecheck/lint/test/build/`npm audit --audit-level=high` on every pushed branch (except `production` and `dependabot/**`) and every PR, then `images.yml` builds the `runtime` target once per commit (pushed by digest, Trivy-scanned, tagged `sha-<commit>`/`dev-<commit>` only on a clean scan; an already-scanned commit is reused) and points `:stage` (`master`) or `:dev` (the repository owner's other branches) at it. A manual `docker compose build frontend` here is break-glass only (see root `CLAUDE.md` golden rule 2).
- No build-time config: the same `ghcr.io/...-frontend` image runs unmodified in dev/stage/production — nginx routing chooses the backend, not the build. There is currently no `import.meta.env.VITE_*` read anywhere in `src/`; keep it that way — anything that must differ per environment belongs in the backend's `/api/` response or in nginx, not baked into this image. `VITE_API_PROXY_TARGET` in `vite.config.ts` only steers the **Vite dev-server** proxy for `/api` (local/dev use), and is never read at build time.
- Local dev: on a Mac (never this box), `compose.local.yml` + the root `Makefile` (`make dev-up`) build this Dockerfile's `dev` target with HMR and bind mounts, `VITE_API_PROXY_TARGET` pointed at the local backend container. On this VPS there's no dev container; to see a change live before a release, push its branch: about 5-7 minutes later (CI incl. e2e, the image build, then the deploy agent's next minute) `dev.yuriodev.co.uk` runs it (the last build to finish wins; the terminal's `status` command shows it as `Branch:`; only the images change, nginx routing and the proxy config stay master's), and merging to `master` puts it on `stage.yuriodev.co.uk` the same way — both behind basic auth, credentials at `~/.config/yuriodev/basic-auth.txt` (never print them). Over SSH, `npm run dev` (Vite on :5173, port-forwarded) remains the fastest edit loop.
- Structure: `src/pages/*` compose `src/components/sections/*`; reusable widgets in `src/components/ui/*`; layout in `src/components/layout/*`. One CSS Module per component (`X/X.tsx` + `X/X.module.css`). Colours only through the CSS variables in `src/assets/styles/_variables.css`, with both `[data-theme="light"]` and `[data-theme="dark"]` variants. Font: Fira Code (the private dashboards too: `--dash-font-ui` is `--font-mono`, with `.dashNum` from `assets/styles/dashboard-type.module.css` for data).
- Routes (react-router 7, `src/App.tsx`): `/` portfolio; `/community`, `/courses`, `/dashboard` are ComingSoon placeholders. `/dashboards`, `/dashboards/{personal,work-1,work-2,calendar}` are the private dashboards (sample data behind `src/services/dashboards/source.ts`, own RU/EN i18n, `data-space` palettes `--dash-*` in `_variables.css` section 6): registered in `PAGES` with no `nav`, so the header, palette, footer and terminal never list them; the layout route is `components/dashboards/DashboardShell`. The dashboards define `chrome: false` in `PAGES`: `PageLayout` then renders only the skip link and `<main>` (no site header, footer, section rail, dot canvas, scroll-to-top, palette or help panel); the dashboards bar is their only chrome (the site's own header built from its parts, sticky: the terminal prompt running the current place, `./dashboards/personal` (a server's name for a space or project appears there), the dashboards pages as the site's bordered pills with the current one underlined, a thin divider, then one pill per project that is not archived (the user's projects, live data only; one row that scrolls sideways when there are many, the current pill kept in view), every pill with a decorative 24px mark (`aria-hidden`: a space's hub-card mark, a project's tile, and the drawn `grid` and `calendar` icons for All and Calendar), a link back to the portfolio, RU/EN and the theme button in the site's control style from `Header.module.css`, which the bar imports without changing; on a phone the short prompt and the pages scroll sideways, and the two switches move to the page end), and their content sits in a 72rem column (the calendar 96rem) instead of the site's content column. The look is the platform's own, from the approved mockup: Fira Code throughout, the site's navy night and pale day with cyan line work and amber headings (each title led by a cyan `# `), soft colour glows on the page (a fixed layer in `DashboardShell`), and glass over them (`.glassDash` in `recipes.module.css`: the skin's surface at its glass alpha, a hairline border, an inset highlight and a drop, blurred 24px) for the bar, panels, strip, hub cards and the calendar frame. Each space is a skin of it, set by `data-space` on the dashboards root in `_variables.css` section 6: Personal is the site palette, Work 1 violet (lavender headings), Work 2 red with black and white; the hub, calendar and projects are the site palette. Every colour is a `--dash-*` token (page, glows, surface, glass alpha, chip, well, border, line, edge, t1..t3, heading, accent, fill, danger/warn/ok, per-space ink/fill/tint, per-card `--hub-*` tints: a hub card is the neutral glass at rest (colour only in its tile, name and "Next:" label) and, on hover, keyboard focus and press, ONE flat tint of its scheme with a coloured border and numbers in its ink (never a gradient; a touch screen stays at rest), the whole card one real link (the title's anchor stretched over it, so the heading must not be `position: relative`); the header card is one flat tint; the three spaces have their own colours, and projects have ONE scheme, Anthropic's brand: clay #D97757 on warm ivory in the light theme and warm near-black in the dark one (`--hub-project-*`; a project's page wears the same as its skin, `data-space="project"` on the shell root, with the clay page glow)), so `contrast.test.ts` holds every text and UI pair per skin and theme on the page, the glass and each glow; `dashboards-design.test.ts` holds the rest (one face, five type steps, weights 400 to 700, the spacing scale, three radii and the pill, colour only from tokens, shadows only from tokens, glows in the shell only, glass only through the recipe, no gradient wash in a card or panel, `--hub-*` read only by the hub's header, cards and project tile). Projects: ONE client-side list (`services/dashboards/projectsStore.ts`, read through `hooks/useProjects.ts`: the hub's cards, a project page and the bar all read it, and create, rename, icon and archive update it in place); each project has an optional `icon` key (`^[a-z0-9-]{1,24}$`, `null` clears) drawn from the hand-made set in `components/dashboards/ProjectIcon` (24px grid, 1.75 stroke, `currentColor`; an unknown key shows the name's letter), picked in a radio grid (`IconPicker`) in the new-project form and next to Rename. Rows stay one line, tabs have no icons, the bar is sticky: the skin is a visual layer, not a layout. App.css gives every `main section` auto side margins: the dashboards shell resets that for its own sections.
- API calls: `GET /api/posts` (the social feed, `services/postsApi.ts`) and, for the private dashboards, `/api/dashboards/v1/*` (`services/dashboards/liveApi.ts`; contract: `GET /bootstrap`, `/summary`, `/spaces/{space}/tasks`, `/events`, writes by `POST`/`PATCH`/`DELETE`). Same-origin relative URLs, no auth header (dev's basic auth is the browser's; the API token is for MCP clients), no build-time config. The dashboards ask `GET /bootstrap` once per page load (`services/dashboards/bootstrapStore.ts`, read through `hooks/useDashboardMode.ts`): `enabled: true` is real data; `false`, a network error, a non-2xx or a non-JSON answer keeps the bundled sample data exactly as before. Space names: `GET /bootstrap` returns `spaces: [{id, name}]`; `parseBootstrap` keeps the names that differ from the bundled English default (`SPACE_NAME[id].en`), and `hooks/useSpaceNames.ts` (`nameOf(space)`) gives the server name in both languages, else the bundled bilingual one; every place that shows a space's name (bar, hub card, hero, calendar legend, event form, week grid, tab title) goes through it. Icons: `parseBootstrap` keeps `spaceIcons` only when they are small base64 data URIs of the same five image types the server accepts (`isIconUri`; never a link, the CSP is `img-src 'self' data:`); `iconOf(space)` gives the image for `SpaceTile` (an `<img alt="">` inside the same 24px tile box) on the live dashboards: the server's icon, else for `personal` the site's own mark (`assets/site-mark.svg`, a copy of `public/favicon.svg`: keep them in step), else the letter or number tile; the sample data always keeps the letters. Until the answer is in, the shell shows a quiet placeholder (never sample data that then swaps). In tests `setupTests.ts` primes the answer as "no answer" (sample data) before every test; live tests call `resetBootstrap()` and install `test/dashboardsApiMock.ts` (an in-memory fake of the contract as the global fetch). Every live request has its own loading and error state with a retry, so one failure leaves the page usable. Projects (`GET|POST /projects`, `PATCH /projects/{id}`, and a project's tasks under `/projects/{id}/tasks[/{task_id}]`, the space endpoints' task shape with `project_id` for `space_id`; `GET /bootstrap` also lists the not-archived ones) live at `/dashboards/projects/:id`, a page outside `PAGES` that `data/site.ts` (`projectPath`, `isProjectPath`, `chromeAllowedAt`) treats as chrome-less like the other dashboards pages; the hub's Projects section (`ProjectCards`, with the inline new-project tile) and the project page exist on real data only, and on the sample data the route shows a not-found state. A task list is addressed by a `TaskScope` (a space id, or `{ project }`): `useLiveTasks(scope)` and the `liveApi` task functions serve both (a project's task is patched and deleted under its project, so those take the scope), and `LiveTask` has `space` or `projectId`. Projects use the neutral tile and ink (no fourth brand palette). Other than these there is no business endpoint for the frontend to call (`GET /health` and `/api/health` are for monitors).
- Dead files (don't extend): `community.html`, `courses.html`, `dashboard.html` (legacy multi-page entries), the 0-byte files in `public/`, `tmp/`, `generate_project_doc.py`, `show_docs_tree.sh`, `*.tsbuildinfo` at the frontend root.
