# Frontend: React 19 + Vite 7 + TypeScript 5.9 (npm)

- Scripts (run in `frontend/`): `npm run dev` (vite on :5173; over SSH use VS Code port forwarding), `npm run build` (`tsc -b && vite build` -> `dist/`, gitignored), `npm run lint` (eslint 9 flat config), `npm run test` (`vitest run`; jsdom environment, `src/setupTests.ts`, see `App.test.tsx`), typecheck only: `npx tsc --noEmit -p tsconfig.app.json` (clean).
- `npm run lint` must stay at 0 problems: it blocks CI (and therefore image builds and every deploy). `npm run test` and `npm run build` block CI too.
- The build runs inside Docker (`npm ci` on node:26-alpine), so `package-lock.json` must stay in sync with `package.json`. Dependency changes (`npm install ...`) need Yurii's OK.
- Builds happen in GitHub Actions, not on this box: `.github/workflows/ci.yml`'s `frontend` job runs typecheck/lint/test/build/`npm audit --audit-level=high` on every pushed branch (except `production` and `dependabot/**`) and every PR, then `images.yml` builds the `runtime` target once per commit (pushed by digest, Trivy-scanned, tagged `sha-<commit>`/`dev-<commit>` only on a clean scan; an already-scanned commit is reused) and points `:stage` (`master`) or `:dev` (the repository owner's other branches) at it. A manual `docker compose build frontend` here is break-glass only (see root `CLAUDE.md` golden rule 2).
- No build-time config: the same `ghcr.io/...-frontend` image runs unmodified in dev/stage/production — nginx routing chooses the backend, not the build. There is currently no `import.meta.env.VITE_*` read anywhere in `src/`; keep it that way — anything that must differ per environment belongs in the backend's `/api/` response or in nginx, not baked into this image. `VITE_API_PROXY_TARGET` in `vite.config.ts` only steers the **Vite dev-server** proxy for `/api` (local/dev use), and is never read at build time.
- Local dev: on a Mac (never this box), `compose.local.yml` + the root `Makefile` (`make dev-up`) build this Dockerfile's `dev` target with HMR and bind mounts, `VITE_API_PROXY_TARGET` pointed at the local backend container. On this VPS there's no dev container; to see a change live before a release, push its branch: about 5-7 minutes later (CI incl. e2e, the image build, then the deploy agent's next minute) `dev.yuriodev.co.uk` runs it (the last build to finish wins; the terminal's `status` command shows it as `Branch:`; only the images change, nginx routing and the proxy config stay master's), and merging to `master` puts it on `stage.yuriodev.co.uk` the same way — both behind basic auth, credentials at `~/.config/yuriodev/basic-auth.txt` (never print them). Over SSH, `npm run dev` (Vite on :5173, port-forwarded) remains the fastest edit loop.
- Structure: `src/pages/*` compose `src/components/sections/*`; reusable widgets in `src/components/ui/*`; layout in `src/components/layout/*`. One CSS Module per component (`X/X.tsx` + `X/X.module.css`). Colours only through the CSS variables in `src/assets/styles/_variables.css`, with both `[data-theme="light"]` and `[data-theme="dark"]` variants. Font: Fira Code, with one exception: the private dashboards set their interface in Fira Sans (self-hosted latin + cyrillic 400/500/600 in `src/assets/fonts`, `@font-face` in `assets/styles/dashboard-fonts.css`, loaded only by `DashboardShell`, token `--dash-font-ui`) and use Fira Code only for data through `assets/styles/dashboard-type.module.css` (`.dashNum`). The public site stays Fira Code only.
- Routes (react-router 7, `src/App.tsx`): `/` portfolio; `/community`, `/courses`, `/dashboard` are ComingSoon placeholders. `/dashboards`, `/dashboards/{personal,work-1,work-2,calendar}` are the private dashboards (sample data behind `src/services/dashboards/source.ts`, own RU/EN i18n, `data-space` palettes `--dash-*` in `_variables.css` section 6): registered in `PAGES` with no `nav`, so the header, palette, footer and terminal never list them; the layout route is `components/dashboards/DashboardShell`. The dashboards define `chrome: false` in `PAGES`: `PageLayout` then renders only the skip link and `<main>` (no site header, footer, section rail, dot canvas, scroll-to-top, palette or help panel); the dashboards bar is their only chrome (a sticky 48px glass bar: brand link, the pages as text links, RU/EN, theme toggle on the site's theme context; on a phone only the pages, the two switches move to the page end), and their content sits in a 72rem column (the calendar 96rem) instead of the site's content column. The look is the "calm tool" system: one neutral ramp, a space colour in five places only, flat 40px rows, glass only on the bar, panels, hub cards and the calendar frame over quiet glows; `dashboards-design.test.ts` holds the type, weight, spacing and radius rules. App.css gives every `main section` auto side margins: the dashboards shell resets that for its own sections.
- API calls: `GET /api/posts` (the social feed, `services/postsApi.ts`) and, for the private dashboards, `/api/dashboards/v1/*` (`services/dashboards/liveApi.ts`; contract: `GET /bootstrap`, `/summary`, `/spaces/{space}/tasks`, `/events`, writes by `POST`/`PATCH`/`DELETE`). Same-origin relative URLs, no auth header (dev's basic auth is the browser's; the API token is for MCP clients), no build-time config. The dashboards ask `GET /bootstrap` once per page load (`services/dashboards/bootstrapStore.ts`, read through `hooks/useDashboardMode.ts`): `enabled: true` is real data; `false`, a network error, a non-2xx or a non-JSON answer keeps the bundled sample data exactly as before. Space names: `GET /bootstrap` returns `spaces: [{id, name}]`; `parseBootstrap` keeps the names that differ from the bundled English default (`SPACE_NAME[id].en`), and `hooks/useSpaceNames.ts` (`nameOf(space)`) gives the server name in both languages, else the bundled bilingual one; every place that shows a space's name (bar, hub card, hero, calendar legend, event form, week grid, tab title) goes through it. Until the answer is in, the shell shows a quiet placeholder (never sample data that then swaps). In tests `setupTests.ts` primes the answer as "no answer" (sample data) before every test; live tests call `resetBootstrap()` and install `test/dashboardsApiMock.ts` (an in-memory fake of the contract as the global fetch). Every live request has its own loading and error state with a retry, so one failure leaves the page usable. Other than these there is no business endpoint for the frontend to call (`GET /health` and `/api/health` are for monitors).
- Dead files (don't extend): `community.html`, `courses.html`, `dashboard.html` (legacy multi-page entries), the 0-byte files in `public/`, `tmp/`, `generate_project_doc.py`, `show_docs_tree.sh`, `*.tsbuildinfo` at the frontend root.
