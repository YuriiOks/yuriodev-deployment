# Infra rules: compose, nginx proxy, Dockerfiles

- `nginx-proxy/` is bind-mounted into the running `yuriodev-proxy` at `/etc/nginx/conf.d`: an edit there goes live at the next reload or restart. After each edit run `docker exec yuriodev-proxy nginx -t` yourself; reload (`docker exec yuriodev-proxy nginx -s reload`) only with Yurii's OK. A failed reload keeps the old config; a proxy restart with a bad config is a full outage.
- Upstreams are resolved per request (`resolver 127.0.0.11` + `set $var http://<container_name>:<port>; proxy_pass $var;`): recreating frontend/backend needs no proxy reload, and a stopped container only fails its own location. Keep this pattern for every new vhost and address containers by `container_name`, never by service name (service names can repeat across compose projects on `yuriodev-network`, and Docker would round-robin between them). Never add static `upstream {}` blocks.
- `docker-compose.yml` edits take effect on the next `up` of the affected service; validate them with `docker compose -f <file> config --quiet` and `python3 scripts/check-compose.py` (CI's `guards` job runs both). Changing the proxy's ports or volumes needs `docker compose up -d --no-deps proxy` (a ~2 s full-site blip; ask).
- Images: GitHub Actions builds each green `master` commit once (`.github/workflows/ci.yml` -> `images.yml`) and pushes `ghcr.io/yuriioks/yuriodev-{frontend,backend}:sha-<commit>`, then points `:dev` at that digest. The packages are public (anonymous pull, no registry login on this box). Promotions only retag existing digests; never delete `sha-*` tags that were ever promoted (rollback depends on them). Workflow files are pushed over SSH (the local gh token has no `workflow` scope) and every action must be pinned to a full commit SHA (repo setting).
- Environments on this host, one proxy: `yuriodev.co.uk` (root `docker-compose.yml`), `dev.yuriodev.co.uk` (`deploy/dev/compose.yml`, `:dev` = every green master commit) and `stage.yuriodev.co.uk` (`deploy/stage/compose.yml`, `:stage` = a `vX.Y.Z-rc.N` tag via `promote-stage.yml`, or every green master commit while repo variable `STAGE_AUTO_PROMOTE=true`). Dev and stage sit behind basic auth (`nginx-proxy/auth/envs.htpasswd`, gitignored; the plaintext lives in `~/.config/yuriodev/basic-auth.txt`), with noindex and no-store. Service names are environment-unique (`frontend-dev`...); never reuse `frontend`/`backend` in another compose project on `yuriodev-network`.
- Env config (`env/`): every compose file's backend service loads `env/<env>.env` (tracked, public: `ENVIRONMENT`, `API_TITLE`, `API_VERSION`, `CORS_ORIGINS`, `LOG_LEVEL`) then an optional `env/<env>.secrets.env` (gitignored, mode 600, created on the machine that runs that env — `required: false` in the long `env_file` form). Template for secret names: `env/secrets.env.example`. To change a value: edit `env/<env>.env`, commit, then on the box `touch ~/.yuriodev-deploy-paused`, `docker compose -f <file> up -d --no-deps <backend svc>`, check `/health`'s `environment`, `rm ~/.yuriodev-deploy-paused` — the deploy agent never reacts to env-file edits by itself, only to image changes, so this recreate step is always manual. `backend/.env` and `deploy/{dev,stage}/backend.env` are legacy (pre-`env/`) and scheduled for deletion; don't add to them.
- Image stages: every Dockerfile builds through named stages and only `target: runtime` ever ships (enforced by `scripts/check-compose.py` in CI's `guards` job). Frontend: `deps` -> `dev` (Vite :5173, local compose only) / `builder` -> `runtime` (LAST; `nginx:stable-alpine`, `apk upgrade --no-cache`, HEALTHCHECK, `frontend/nginx.conf` baked in). Backend: `base` -> `builder` (wheels) -> `dev` (`uvicorn --reload`, `requirements-dev.txt`) -> `runtime` (LAST; installs only from prebuilt wheels — no network, no compiler — then strips `wheel`/`setuptools`/`jaraco.*`/`pkg_resources` (`pip` stays); runs as non-root uid 10001 `app`; HEALTHCHECK via `python -c "urllib.request.urlopen(...)"`; `ARG GIT_SHA` -> `ENV REVISION`, surfaced by `/health`). Both base images are pinned by digest (`node:22-alpine@sha256:...`, `nginx:stable-alpine@sha256:...`, `python:3.11-slim@sha256:...`); Dependabot's `docker` ecosystem entry refreshes the pins weekly (major/minor bumps to `python`/`node` are ignored — bump by hand).
- Deploy agent: `deploy/agent/yuriodev-deploy.sh` runs from the user crontab every minute with `ENABLED_ENVS`, pulls each environment's images and, only for a service whose pulled image ID differs from the running container's, recreates it (`docker compose up -d --no-deps <svc>`) then waits for it to come healthy: if the image defines a `HEALTHCHECK`, it polls `docker inspect`'s `.State.Health.Status` for up to ~90s; only an image without one (older, pre-HEALTHCHECK images) falls back to a proxied request (`GET /` for frontends, `GET /health` for backends, up to 6 tries 5s apart). Log `~/.local/state/yuriodev-deploy.log`, heartbeat `~/.local/state/yuriodev-deploy.heartbeat`. Kill switch: `touch ~/.yuriodev-deploy-paused` (running containers keep running).
- Only the proxy publishes ports (80, 443). Never add `ports:` to other services.
- Config drift: running containers can carry an older compose config hash than the file, so a bare `docker compose up -d` can recreate services unexpectedly. Always name services and add `--no-deps`; preview with `docker compose --dry-run up -d --no-deps <svc>`.
- Healthchecks: all three services have one. Frontend/backend: a Dockerfile `HEALTHCHECK` (`wget --spider http://127.0.0.1/` / a `python urllib` GET of `/health`), which is what makes the deploy agent's Docker-health wait apply. The proxy (no Dockerfile — it's stock `nginx:stable-alpine`) gets a compose-level `healthcheck:` hitting `http://127.0.0.1/healthz` (the plain-HTTP `:80` server answers `/healthz` directly; the HTTPS redirect lives in that same server's `location /`). `scripts/check-compose.py` requires the proxy to have this healthcheck and forbids giving it a memory limit (it serves every environment).
- Logging: every service in every deployed compose file has the same `json-file` block, `max-size: "10m"`, `max-file: "3"` — enforced by `scripts/check-compose.py` (logging shapes must match across services). Resource limits (`deploy.resources.limits`): prod frontend 128M/0.5 CPU, backend 256M/1 CPU; dev/stage frontend 96M/0.2 CPU, backend 192M/0.4 CPU; the proxy has none on purpose. `docker compose` applies `deploy.resources.limits` natively (no Swarm needed) as a container cgroup limit.
- Vulnerability scanning: `.github/workflows/images.yml` runs Trivy against each freshly built `runtime` image (`severity: CRITICAL,HIGH`, `ignore-unfixed: true`) and **fails the job** — so `:dev` (and `:stage` under `STAGE_AUTO_PROMOTE`) does not move — on any fixable HIGH/CRITICAL finding.
- Monitor: `.github/workflows/uptime.yml` (cron every 10 min) checks, through Cloudflare, that production's `/` is 200 and `/api/health` reports `status: healthy` + `environment: prod`, and compares `revision` against the latest GitHub Release (20-minute grace). A failure opens/updates one issue labelled `monitor` (GitHub emails the repo owner) and it self-closes on recovery. `gh issue list --label monitor --state open` is the fast way to check for an active alert. GitHub disables the cron after 60 days with no commit to `master`.
- Origin TLS: Cloudflare Origin CA cert `nginx-proxy/certs/origin.pem` + `origin.key` (key mode 600, gitignored by the `certs/` rule), served from `/etc/nginx/conf.d/certs/` inside the proxy; valid until 2041-09-20; issued via the Cloudflare API from a key generated on this server. Never commit or print the key. Check with `/cert-status`.
- `certbot/` is the legacy root-owned Let's Encrypt store (expired 2026-05-15, nothing renews it). It stays mounted only because `default.conf` includes `/etc/letsencrypt/options-ssl-nginx.conf` and `ssl-dhparams.pem`; don't edit it.
- Not part of this stack: the host's `/etc/nginx/sites-*` and `certbot.timer` (renews the unused `/etc/letsencrypt`), and `/usr/bin/docker-compose` (legacy v1).
