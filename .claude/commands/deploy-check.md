---
description: Pre-release validation for yuriodev.co.uk - CI green and scanned images for a commit, stage running those images, stage smoke test. Read-only. Use before tagging a release (vX.Y.Z, or an optional rc).
argument-hint: "[ref, default: origin/master]"
---
Target commit: `$ARGUMENTS` (a ref/SHA; default the tip of `origin/master`). Run everything from /home/yurii/yuriodev-deployment.

1. **What ships.** `sha=$(git rev-parse <ref>)` for the full 40-char commit SHA used below as `<sha>` (image tags are `sha-<full-sha>`, not the abbreviated form `git log --oneline` prints), plus `git log -1 --oneline <ref>` for a human-readable summary; confirm it is on `master`: `git merge-base --is-ancestor <ref> origin/master && echo ok`.
2. **CI green for this commit.** `gh run list --workflow=ci.yml --commit <sha> --limit 5` — the `frontend`, `backend` and `guards` jobs must all have succeeded: `frontend` includes typecheck, lint (0 problems, blocking), `npm run test`, build and `npm audit --audit-level=high`; `backend` is `ruff check`, `ruff format --check`, `mypy` (strict), `python -m pytest -q --cov` with a 90% branch-coverage gate and a Trivy scan of `backend/requirements.txt`'s pins (fixable HIGH/CRITICAL fails it); `guards` is `scripts/check-compose.py` plus `docker compose ... config --quiet` on every compose file. None of these `continue-on-error`. The proxy's Trivy scan is a separate workflow (`gh run list --workflow=proxy-image.yml --limit 3`): report its state, but it does not gate app releases (the proxy is rolled out by hand, `deploy/README.md` "The proxy image").
3. **Images built for this commit.** The registry is the source of truth: `docker buildx imagetools inspect ghcr.io/yuriioks/yuriodev-frontend:sha-<sha>` and `...-backend:sha-<sha>` (anonymous pull, no login needed). `images.yml` adds a `sha-<sha>` tag only after Trivy found no fixable HIGH/CRITICAL CVE, so the tag existing is the proof. For the run itself: `gh run list --workflow=images.yml --limit 10` and read the titles (`Images: master @ <sha>`); Images runs are filed under master's tip, so never filter them by `--commit`/`--branch`.
4. **Stage is running those images** (meaningful before a release tag, not an rc; stage follows the newest built `master` head, so for the tip of `origin/master` this holds once both its images are built, while an older master commit needs an rc tag first): compare digests — `docker buildx imagetools inspect ghcr.io/yuriioks/yuriodev-{frontend,backend}:stage` against the `:sha-<sha>` digests from step 3. This is exactly the gate `promote-production.yml` enforces.
5. **Stage smoke test.** `.claude/scripts/smoke-test.sh` (it already checks stage's containers, basic-auth gating and reachability alongside prod/dev) plus `curl -sk --resolve stage.yuriodev.co.uk:443:127.0.0.1 -u <user>:<pass> https://stage.yuriodev.co.uk/api/health` to confirm `environment: stage`, a `revision` matching `<sha>` and `ref: master` (credentials in `~/.config/yuriodev/basic-auth.txt`, never print them).
6. **Resources.** `free -m` (need >= 1500 MiB available for anyone building locally), `df -h /`.

Output: a table (check, result, evidence) and the exact release commands for Yurii to approve (see `/deploy`). This command never tags, pushes, builds or deploys anything.
